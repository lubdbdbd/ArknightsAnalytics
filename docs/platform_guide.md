# Arknights Analytics 可视化运营工作台

## 定位与技术栈

围绕「ERP数据处理、商品信息维护、衍生品周边用户调研」构建可操作的本地工作台，而不是只有截图的静态看板。

参考 SakikoMind 的 Vue 3 / Vite / FastAPI 前后端分离结构，沿用 Python、SQLite、pytest，并提供 Redis、Nginx、Prometheus 与 Docker Compose 配套。分析计算继续使用现有 Pandas / SQL 管道。当前业务没有独立 Flask 服务或向量检索需求，因此不为堆叠技术栈引入 Flask、ChromaDB。

## 启动

需要 Python 3.11+、Node.js 22+ 和 pnpm。首次准备环境：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
cd frontend
pnpm install --frozen-lockfile
pnpm build
cd ..
.\.venv\Scripts\python.exe scripts/run_platform.py
```

打开 http://127.0.0.1:8765/ 。接口文档位于 `/docs`，监控指标位于 `/metrics`。

默认读取 `data/processed` 中已有的分析结果，不会启动采集或重写问卷。不要为展示界面重新生成模拟数据。

端口占用时使用 `scripts/run_platform.py --port 8766`。旧专项问卷门户与此工作台是两个独立服务；如需同时运行，使用 `scripts/run_pilot_portal.py --port 8767` 启动问卷，不要共享8765端口。

开发模式：保持后端8765运行，在 `frontend` 内执行 `pnpm dev`，访问5178；Vite代理 `/api`、`/metrics` 到后端。

## 周边商业化运营定向能力

首页新增运营简报，按「发现—建议动作—核对标准—来源」组织商品维护、ERP风险和用户调研三类工作，支持Markdown导出。它依据当前快照及人工主档进行确定性汇总，不调用LLM，不替代人工审批，不将建议写为已完成动作。

ERP页新增「渠道复盘」，展示7个模拟渠道的订单支付率、支付客单价、退款金额率和退款后毛利代理。直播间153张订单、144张支付订单来自模拟数据，不代表抖音实操经验。未接入曝光、进房、点击、投流及真实场次，所以不推算漏斗和ROI；页面提供开播前、中、后协作清单作为准备。

`GET /api/operations/brief`读取简报，`?download=true`导出。调研候选在样本至少30份的品类中排序，此为探索规则，不代表统计显著性或立即备货建议。

## 商品主数据治理

内部主档以 `sku_code` 标识商品；公开档案以淘宝 `item_id` 派生外部商品编码。维护层使用独立 SQLite 数据库 `data/runtime/platform.db`：

- `catalog_overrides` 保存字段覆盖值和版本，不覆盖源CSV。
- `catalog_audit` 保存实体、时间、版本、修改原因、字段前值和后值。
- 售价、成本、库存策略、生命周期和标准品类等字段执行服务端校验；成本必须低于售价，再订货点不能低于安全库存。
- 公开页面授权标签与人工授权核验是两个独立字段。提供证据URL仅代表操作者提交复核依据，平台不自动证明授权有效；核验人员仍须检查证据内容。
- 乐观锁阻止旧版本覆盖新修改，返回409后需要重新读取数据。
- 历史ERP金额、补货报告保持原分析时点口径。修改现价或库存策略不会偷偷回算历史报表；需要新分析批次时应明确重跑对应管道。

CSV维护示例（仅示范格式，不代表需要实际调价）：

```csv
sku_code,price,unit_cost
AK-0001,48,16.8
```

每批最多500条，仅接受已存在SKU和白名单字段。预检不写数据库；预览明确标记重复SKU、无效值、未知编码和列数异常。确认后逐条保存有效行，遇到版本冲突停止后续行，并显示已保存数量。它不是跨整批原子事务，不应描述成“整批失败全部回滚”。

内部/公开档案导出沿用当前筛选条件。CSV使用UTF-8 BOM并防护公式前缀，便于Excel核对。

## ERP对账口径

订单查询、对账结果、CSV导出使用同一组已提交筛选条件；导出包含整个查询范围而非当前分页。

1. 表头商品金额对比明细 `quantity × unit_price` 合计。
2. 表头优惠对比明细优惠合计。
3. 已支付订单实付对比「商品额 − 优惠 + 运费」，已取消订单预期实付为零。
4. 检查缺失明细、重复订单头、重复明细ID和非法支付状态。
5. 全库额外统计找不到订单头的孤立明细，该项明确标注全库口径。

金额差值保留两位小数，绝对差值大于0.01元列为异常。页面最多展示100笔异常的细节，异常总数不截断。对账通过仅代表这些规则成立，不证明外部支付平台已到账；该项目尚未接入支付账单。

## API与部署

- `/api/overview`：真实读取当前分析快照汇总。
- `/api/data/{dataset}`：白名单数据集、检索、分页、日期与渠道筛选。
- `/api/catalog/{domain}`、`PATCH /api/catalog/{domain}/{entity_id}`：有效工作主档查询与版本化更新。
- `/api/import/preview`、`/api/audit`：批量预检与变更历史。
- `/api/erp/reconciliation`：订单对账计算。
- `/api/export/{dataset}`：当前筛选范围导出，不暴露原始问卷。

可选容器运行：

```powershell
docker compose up --build -d
```

Compose配置包含Nginx入口8765、FastAPI、Redis缓存和Prometheus9091。SQLite工作数据持久化到 `platform_state` 卷。启动前停止占用8765的本地平台。当前已验证Compose配置解析，尚未执行完整镜像构建与容器联调；本地运行不会假装Redis/Prometheus服务器已经启动。

默认只绑定127.0.0.1，不具备生产环境的登录、角色权限或多人审批。跨来源写请求会被拒绝，但这不替代认证。不要直接暴露到公网；上线前补充身份认证、权限隔离、备份恢复、TLS与部署验收。问卷原始回答及私有运行数据库不提交GitHub。

## 决策证据复现

进入 `/#decisions`，用“重新计算”重读当前输入，或访问 `GET /api/decision-evidence`；加 `?download=true` 导出说明。离线执行：

```powershell
.\.venv\Scripts\python.exe scripts/build_decision_evidence.py
```

输出位于 `reports/generated/decision_evidence/`，包含报告、209组情景明细、60名角色稳定性、SQL渠道结果和输入SHA-256清单。种子固定为20260907。旧静态报告需重跑更新，指纹只定位文件版本，不认证数据真实性。页面API省略12,540条实验明细以减少传输，完整明细保存在CSV。
