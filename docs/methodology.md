# 方法与口径

## 1. 研究问题

本项目不预测真实销量，而是验证“公开角色热度如何转化为可解释的选品假设”。核心问题包括：

1. 哪些角色在官方公开内容中具有较高关注度与互动质量？
2. 不同周边品类的价格、毛利、直播适配度和生产风险如何组合？
3. 用户表达的购买意愿能否为角色、品类、价格与渠道选择提供方向性证据？
4. 在缺少真实 ERP 的条件下，如何构建透明、可复现且不会冒充真实业务的数据演示？

## 2. Heat Score

首先按照视频发布天数计算播放速度，再计算加权互动率、收藏率和分享率。各指标使用样本内百分位转换为 0～100 分：

```text
Heat Score = 40% 播放速度 + 30% 加权互动率 + 15% 收藏率 + 15% 分享率
```

该分数只在当前样本中用于相对比较。视频题材、发布时间和平台推荐均可能造成偏差。

## 3. SKU Selection Score

```text
Selection Score
= 30% 角色热度
+ 30% 模拟转化率
+ 20% 模拟毛利率
+ 10% 直播适配度
- 10% 库存风险
```

真实落地时应使用问卷购买意愿、收藏加购、历史销售、退货和库存数据替换模拟指标。

## 4. 数据分层

| 层级 | 示例 | 是否真实 |
|---|---|---|
| Public | 官方视频聚合互动量 | 是，采集时点快照 |
| Manual | 品类运营假设、来源备注 | 人工整理 |
| Survey | 243份匿名问卷、729条角色排序、1,701条品类价格观测 | 是，经批次所有者确认 |
| Simulated | 订单、销量、库存、退货 | 否 |

## 5. 可复现与质量控制

- 原始快照与处理结果分目录保存。
- 平台页面以“万”为单位展示的数据标记为 `display_rounded`，不声称具有个位数精度。
- 模拟数据保留固定随机种子与 `is_simulated` 字段。
- 对角色解析、指标边界和模拟一致性编写自动化测试。
- 接口出现 412、429 或验证码时停止采集，不绕过风控。
# 多平台热度矩阵方法

## 数据层级

1. **角色内容层**：B站官号角色 PV 作为全榜主样本；微博官号近期内容用于交叉验证。
2. **平台生态层**：小红书公开品牌榜衡量《明日方舟》整体笔记量、互动量、收藏率与评论率。
3. **商业验证层**：后续接入淘宝商品数量、付款人数、评价数、收藏加购与价格带数据。

小红书品牌生态数据不直接分配给具体角色，否则会制造所有角色拥有相同平台热度的伪精度。

## 角色评分维度

- **Reach**：累计传播规模。
- **Momentum**：使用发布时间校正后的传播速度。
- **Engagement**：点赞、评论、弹幕等综合互动质量。
- **Intent**：收藏、投币、转发等更接近持续关注或购买意愿的动作。
- **Discussion**：评论和弹幕形成的讨论强度。
- **Consistency**：B站和微博对同一角色排序的一致程度。
- **Confidence**：平台覆盖、内容样本量和数据粒度形成的可信度。
- **Evergreen**：长期触达和互动沉淀。
- **Viral Potential**：近期传播速度与讨论爆发力。
- **Merch Opportunity**：热度、意向、一致性与可信度组成的候选选品分。

角色总分使用 `70% Bilibili + 30% Weibo`。微博缺失时使用中性值 50，但同步降低 Confidence 并标记数据等级，不把缺失误判为低热度。

## Bilibili 官号历史内容层

项目通过公开 related 图低频整理并校验549条官号历史内容，覆盖2019—2026年并划分为8类。角色层只把标题明确包含干员结构的30条PV作为直接角色内容；其余内容若位于最近角色PV前后14天，则标记为`campaign_window`，用于衡量角色上线阶段的共享宣传深度，不直接改写角色热度分。最终形成271条角色Campaign关联，中位每名角色7.5条内容。该设计既扩展内容规模，也通过IP实体黑名单隔离跨项目污染，避免把活动PV、EP或单字误匹配冒充角色自身表现。

## 实体识别

优先识别 `干员「角色名」`、`//角色名` 等明确结构；单字角色不使用普通子串匹配，避免将“望”误识别于“希望/愿望”，或将“余”误识别于“余量”。

## 当前限制

- 微博公开镜像只覆盖近期内容，因此早期角色的微博列为空。
- 小红书开放接口未提供角色级官号笔记读取，本项目仅保留公开品牌生态快照与人工导入模板。
- 热度衡量内容传播，不等于销量；淘宝数据接入后才进行商业转化校准。

## 淘宝商业验证层

### 快照设计

淘宝数据采用固定查询词、固定排序、固定商品 ID 和固定采集日期的周期快照。当前包含一组全 IP 销量页市场基准和一组新约能天使定向销量页，共 84 条公开商品记录。广告跳转位因缺少稳定商品 ID 不进入时间序列。

### 数据质量门禁

1. `sales_proxy_min` 记录页面公开展示的收货人数下界；`100+` 按 100 记录，并设置 `sales_proxy_censored=true`。
2. 定向搜索并不保证每条结果属于目标角色，因此通过异格名、基础名和昵称别名表计算 `target_relevance`。
3. 全 IP 搜索中的《明日方舟：终末地》商品标记为 `ip_scope=endfield`，不参与《明日方舟》角色商业排名。
4. 多角色商品的销量代理按命中角色数等比分配，避免一条商品被重复累计多次。
5. 未观察到淘宝商品的角色记为“未观测”，商业分为 0，不把数据缺失解释为没有消费需求。

### Commercial Heat

```text
Commercial Heat
= 35% Demand Proxy
+ 25% Supply
+ 20% Search Visibility
+ 10% Price Power
+ 10% Assortment Breadth
```

- **Demand Proxy**：公开收货人数下界的样本内百分位。
- **Supply**：可稳定追踪的自然商品数量。
- **Search Visibility**：按搜索排名衰减加权，排名越靠前权重越高。
- **Price Power**：角色商品中位价的样本内百分位。
- **Assortment Breadth**：官方或正版授权商品在亚克力制品、通行证、吧唧（徽章）、毛绒玩偶、手办模玩、装饰摆件和日用生活7类货盘中的覆盖宽度。

该分数只用于首批公开样本内的相对观察，不代表真实市场份额。项目现已建立固定商品注册表、7天复采周期及D/C/B/A证据等级；首批样本仍全部为单期D级基线，达到至少两期且跨越7天后才允许解释销量档位、价格和排名的方向性变化。

## 真实用户调研层

匿名问卷只调查官方或正版授权实体周边，排除盗版、无授权商品和数字权益；只保存批次内匿名编号，不采集姓名、手机号、邮箱、微信、IP或住址。当前批次共243份，拆分为243条受访者主记录、729条角色Top-3排序和1,701条全品类价格观测。原始文本未导出提交时间和填写时长，因此采用`anonymous_batch_without_timing`校验配置，只校验25题完整性、重复答案、角色排序、品类、购买意愿和价格范围，不虚构补全缺失字段。问卷结论仍属于便利样本，只用于小批量验证，需继续通过收藏、加购、付款、退款和复购数据确认。

## 可验证选品案例

选品案例采用六层证据门禁：跨平台内容热度、深层互动意向、定向搜索质量、淘宝需求下界代理、固定SKU时间序列和真实匿名用户调研。前四层通过但后两层缺失时只允许标记为`conditional_pilot`，不能包装为已经验证的商业机会。

### 周边运营决策矩阵

- **核心商业角色**：内容热度和商业信号均高，适合扩品类和组合套装。
- **内容热、商业供给待验证**：优先补采定向搜索、收藏和评价，适合低成本小批量测试。
- **内容长尾但商品信号较强**：检查是否存在核心圈层、联名活动或特定品类偏好。
- **低成本观察**：维持基础款，等待版本活动或角色剧情带来的新增信号。

## SQL 运营决策层

SQLite 不只作为结果存储，而是承担可复核的业务计算层：

1. 使用角色名作为主键，将内容热度、淘宝商业信号和 SKU 经营数据连接为统一决策看板。
2. 使用 `ROW_NUMBER` 对每名角色和每个品类分别排名，避免全局高热角色挤压长尾候选。
3. 使用 `PERCENT_RANK` 计算 SKU 在同品类中的相对位置，使不同价格与成本结构的商品可比较。
4. 使用 CTE 与 `CASE WHEN` 建立价格带、风险等级、商业象限和推荐动作。
5. 使用条件聚合与 `NULLIF` 计算加权转化率、售罄率、退货率、正版占比、预售占比和服务覆盖率。
6. 使用窗口聚合计算 Top 10 销量代理集中度，识别需求是否过度集中于少数搜索结果。
7. 使用数据质量视图标记跨 IP、目标角色不相关、销量缺失和档位截断商品，决定是否允许进入时间序列。
8. 对商品 ID、快照日期、角色、品类和验证优先级建立复合索引，支持周期复采后的增量查询。

## ERP 经营数据处理层

1. 以30名角色×7类正版周边生成210个模拟SKU主数据，维护售价、成本、供应商、采购提前期、安全库存和再订货点。
2. 使用问卷中的角色Top-3、首选品类和购买渠道占比作为需求权重，生成90天订单链路；订单事实仍标记为模拟，避免把意愿数据冒充成交。
3. 将订单拆分为Order Header与Order Line，通过SQL核对订单金额、优惠分摊与明细净收入，当前6,000张订单全部通过0.01元容差对账。
4. 按SKU×日期维护期初、入库、需求、销量、缺货、退货、残损、期末、锁定和可售库存，形成18,900条库存日快照。
5. 当可用库存触及Reorder Point时自动生成Purchase Order，并模拟供应商提前期、延期和缺交，区分received与open状态。
6. 将退款、退货、换货与原因、影响数量、退款金额和关闭时长写入After-sales表，支持按SKU、品类和原因进行Pareto分析。
7. 汇总Net Sales、COGS、Gross Profit、Gross Margin、Return Rate、Sell-through Rate、Inventory Turnover、Days of Inventory和Stockout Rate，输出补货、滞销及高退货动作建议。
