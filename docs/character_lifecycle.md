# 角色生命周期观察

## 业务用途

把静态选品排名扩展为“角色—事件—时间—证据—下一步”。这个模块服务于商品立项前的分阶段观察，不会把缺少内容或旧角色直接判断为衰退，不改写原209组排序稳健性实验。

运行 `python scripts/build_lifecycle.py`，在工作台打开 `/#lifecycle`。可使用 `--as-of 2026-09-03` 回看截至某日已采集的信息。默认基准为输入中最近的采集日期；页面支持指定日期、角色搜索、阶段筛选、查看来源、导出Markdown报告及完整JSON证据。

## 数据如何进入分析

1. 候选名单来自 `operator_demand_fusion.csv`，保留全部60名角色。
2. 官号内容使用既有 `explicit_operator` 和 `official_content_scores` 的直接角色关联，不用模糊标题搜索扩张关联，不把±14日Campaign背景算作角色独占曝光。异格与原角色保持原名单身份。
3. 合并B站历史库及 `data/public/expansion/*/bilibili_observations.json` 中的公开复采。平台+内容ID+采集时点去重，同一时点冲突报错。不同平台不合并互动总量。
4. 将直接内容发布时间登记为宣传事件。PV日期不是角色实际上线日，未自动填充上线日期。人工补充上线、剧情、联动、周年或宣传事件时，写入 `data/manual/lifecycle_events.json`，必须包含官方来源及核验说明。
5. 原问卷没有提交日期，商品首批为横截面，因此这两类证据仅用于选品背景，不能据此计算时间趋势、转化或生命周期需求变化。

## 两条不同的判断轴

**事件阶段**：已核验上线事件后28日内为“导入观察期”；近期直接宣传或已核验活动为“事件观察期”；有历史记录但无近期事件为“阶段待验证”；无记录为“观察不足”。上线与宣传事件必须区分。28日为探索假设，可在配置中调整，不是行业标准。

**内容趋势**：至少2条相同B站内容，在3个连续7日区间内都有有效复采，采集时间偏差不超过0.05日，才比较日均播放增量；连续相邻区间均增长20%以上标为“内容增速上升”，均下降20%以上标为“内容增速回落”，均在±20%内为“相对平稳”，其余为“波动”。缺失不插值、负增量不归零、零基数不生成无限增长率。以上只描述内容计数，不能证明角色需求增长；内容年龄及推荐分发仍是混杂因素。

单次复采区间的日均播放增量＝（后次累计播放－前次累计播放）÷实际间隔天数。不能以累计播放÷视频年龄代替最近增长，也不能把不同视频的累计量差作趋势。

## 时间轴与事件窗口

- 60名角色×26周共1,560条派生记录，按北京时间周一分组；最近一周可能尚未结束。
- 周记录只统计收录样本内的直接内容。零条意味着未收录，不代表真实零内容或零关注。多角色共享直接内容另有1/N分摊字段。
- 每个直接事件形成前28日和后28日窗口，排除事件锚点本身，显示其他收录内容数量与后窗口是否结束。即使窗口日历结束，也不声称平台全量覆盖。
- 没有完整连续观察和对照，事件窗口不计算活动提升率、不作差分因果结论。

## 后续补采步骤

每名角色都有观察建议，包含固定内容ID、建议下次复采日与事件核验任务。建议不是已执行记录，也没有自动创建定时抓取。

1. 优先核对近期活动角色的官方上线/剧情/联动公告，保留链接、日期、适用角色和人工核验依据。
2. 固定同一队列每7日复采一次，至少形成4个时点以构成3个区间；尊重平台已有采集限制。建议日期相对数据最后采集日计算，若已过期则及时补采，不能倒填。
3. 对新发布内容另行记录固定发布年龄（如7日和30日）观测，未来用于同类型内容比较；当前历史库不伪造这些历史时点。
4. 问卷下一批增加采集日期及活动背景；商品连续采集保持同一商品ID，公开“已售”模糊区间不转为精确销量。

人工事件记录结构（结构示例，非真实事件，不可直接导入）：

```json
{
  "event_id": "unique-event-id",
  "operator": "候选名单中的角色",
  "event_type": "release",
  "event_at": "YYYY-MM-DDT00:00:00+08:00",
  "title": "官方公告标题",
  "source_url": "https://官方公告地址",
  "verified": true,
  "evidence_note": "具体哪一段确认了这个角色的上线日期"
}
```

输出包含输入SHA-256、规则版本、逐角色结论、时间轴、复采区间、事件窗口和待补证据，便于复核。原始数据不回写。
